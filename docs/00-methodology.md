# 00 · 方法论总纲

## 1. 「成熟」的判定标准

一个移植方法成熟与否，不看它能把某个 mod 跑起来，而看它是否满足四个可检验的属性：

| 属性 | 含义 | 本仓库的兑现方式 |
|---|---|---|
| 可复现 | 同一输入 + 同一版本 → 逐字节相同输出 | 确定性分诊器、版本化规则库、`content_hash` 冻结 |
| 可回归 | 改了规则或转换器，能立刻知道破坏了什么 | golden 用例、`validate.py` 集群自检、差分测试 |
| 可度量 | 能回答「这个 mod 有多难移」「还差多少」 | C6 占比、证据覆盖率、能力缺口清单 |
| 可增量 | 单个单元可独立重跑，不必重跑整个 mod | delta 协议 + 幂等键 + 单元级 manifest |

反过来，**一次性生成的代码文本**四条都不满足，因此它不是本仓库的合格产物。

## 2. 三层结构：把不确定性隔离出去

Horizon 的运行时架构目前未知。与其猜，不如把它隔离在一条明确的分界线之后：

| 层 | 内容 | 是否依赖 Java/Forge | 是否依赖 Horizon |
|---|---|---|---|
| `source facts` | 反编译字节码/源码的事实、分类标签、耦合图 | 是 | 否 |
| `portable contract` | 平台无关的行为契约：状态机、数据流、事件时序、资源引用、能力需求 | 否 | 否 |
| `target binding` | 把能力需求绑定到 Horizon 的具体实现 | 否 | 是 |

上游几十个 skill 只写前两层。Horizon 架构确定、或日后改动时，只改 `target/horizon.capabilities.json` 与下游绑定 skill，**上游一行不动**。契约层里只允许出现 capability id（见 `capabilities/vocabulary.json`），不允许出现任何 Rust 类型、trait、ECS 术语或 Java 类名。

这条分界线也是「可移植」的定义：**可移植的是契约，不是实现。**

## 3. S0–S5 流水线

| 阶段 | 输入 | 执行者 | 产物 | 硬性要求 |
|---|---|---|---|---|
| S0 规范化 | mod jar | 机器 | 解包、反编译、class 双轨留存、mappings、校验和 | 源码与字节码都保留；字节码是 ground truth |
| S1 机械分诊 | artifact-index | 机器 | 初版 manifest | 100% 单元覆盖，确定性，零模型参与 |
| S2 建图切簇 | 初版 manifest | 机器 | 调用图、常量池跨层边、功能簇 | 必须扫字符串常量池 |
| S3 语义裁决 | 低置信/冲突单元 | 模型 | 带证据引用的标签 delta | 只处理被 S1 标出的单元，输出必须可回溯 |
| S4 人工关卡 | C6 与语义等价项 | 人 | review sheet | 机器与模型都无权替人决定语义等价 |
| S5 冻结 | 已复核 manifest | 机器 | `frozen: true` + `content_hash` | 后续改动一律走 delta / PR，不原地覆写 |

## 4. 三条原则

1. **确定性的归机器，语义的归模型，决策的归人。** 模型不是分类器，是低置信项的裁决器。
2. **分类是活账本，不是一次性报告。** 翻译中途发现混合层，要改标签并触发影响面分析。
3. **产物优先是规则、脚本、映射表、测试夹具，而不是代码文本。**

## 5. 处置路由（C 维）

| 标签 | 含义 | 下游链 |
|---|---|---|
| C1 | 纯算法/状态机，语义稳定，可直译并差分测试 | 逻辑层 |
| C2 | 行为保留，接口按目标侧重新设计（契约化重写） | 逻辑层 + 契约层 |
| C3 | 平台 API 调用，走能力映射表 | 平台层 |
| C4 | 数据/资源，转换器一次性生成 | 数据层 + 美术层 |
| C5 | 舍弃或用目标侧原生机制替身（Mixin、ASM、反射、Java 渲染管线） | 平台层 |
| C6 | 反编译失败、混淆、native、动态生成，需人工裁决 | 人工关卡 |

**C6 占比是本方法最诚实的成熟度指标**：它越高，说明规则库越不完善。

## 6. 验收闭环

- **行为**：Java 侧录制输入序列与状态序列 → Rust 侧重放比对（差分测试），而非比对其源码。
- **资产**：完整性清单、常量池跨层引用闭合检查、贴图通道与动画状态机对齐。
- **视觉**：快照对比，用于 C4/C5 的美术链。
- **跨层契约**：如「射击/装填逻辑状态机 ↔ 骨骼动画状态机」必须在 manifest 中显式记录，任一侧改动触发影响面分析。这类不一致不会导致编译错误，只会产生「逻辑已换弹、动画还在装填」的隐形缺陷，是端到端验证的首要目标。

## 7. 与 TaCZ 的关系

TaCZ 是首个验证样本，因为它同时具备引擎逻辑、平台粘合、数据驱动内容包与重美术资产，能覆盖绝大多数分类路径。本仓库**不记录它的具体类名与包结构**——那些由 `intake-jar` 从真实反编译产物生成，避免把猜测写进方法论。
